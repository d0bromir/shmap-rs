\begin{abstract}
\noindent
\textbf{Summary:} \emph{map-shmap} maps long reads by comparing FracMinHash
sketches under a seed heuristic that prunes candidate regions before refining
them. Its reference implementation is single-threaded and sizes its bucket
accumulator against the \emph{reference}, putting whole-genome mapping outside
ordinary memory budgets. We present \textbf{shmap-rs}, a Rust implementation
that leaves the algorithm untouched --- output is byte-identical --- and
rebuilds the data structures and the parallel decomposition around it. Against
the tuned C++ reference it is \shmSpeedupXMin--\shmSpeedupXMax$\times$ faster
single-threaded, uses \shmRssRatioMin--\shmRssRatioMax$\times$ less peak memory
and makes that footprint a property of the query rather than of the genome, and
adds thread parallelism the reference lacks, reaching \shmScaleXPeak$\times$ on
\shmCoresX{} cores. Every claim is measured on two architectures, whose runs
agree on every algorithmic counter.\\[0.2em]
\textbf{Availability:} \url{https://github.com/d0bromir/shmap-rs}, \shmLicense,
version~\shmVersion. Suite, result sets and the generator of every figure here
are in the repository.\\[0.2em]
\textbf{Contact:} ORCID \shmOrcids.
\end{abstract}

\section{Introduction}

Sketch-based mappers compare a read to a genome in the space of a few thousand
hashes rather than a few billion bases~\cite{mash}.
\emph{map-shmap}~\cite{shmap} sketches read and reference by FracMinHash,
accumulates seed matches into overlapping buckets, prunes them with an
admissible seed heuristic, and refines the survivors with a sliding window. Its
cost is dominated by dependent memory references rather than arithmetic, which
is why it was worth re-engineering rather than re-designing. No change may
alter a single output record, so every number below compares two
implementations of one algorithm.

\section{Implementation}

\textbf{Accumulator sized by the read, not the reference.} The reference
allocates a dense array indexed by reference bucket, so its footprint is a
property of the genome and is paid on every run. A read can only match buckets
within its own span, so shmap-rs sizes the array by the read's half-length and
falls back to a sparse map. Almost the whole memory result, and it removed a
contention bottleneck that had made multithreading nearly useless.

\textbf{Memoised refinement.} The second-best-mapping search repeats scoring
the best-mapping search has done; shmap-rs replays those scores, removing
roughly two calls in five into refinement, for the metrics where replay is
provably sound.

\textbf{Parallelism the reference does not have.} Reference sketching chunked,
index storage sharded by hash, FASTA parsing a two-pass count-then-fill --- all
parallel, none order-dependent, so the index does not depend on how many
threads built it and output stays byte-identical.

\textbf{Hot-loop work.} Repetitive seeds accumulate in place at constant
integer cost rather than through a scratch hash map; the rolling nucleotide
hash~\cite{nthash} keeps rotations precomputed and iteration free of bounds
checks; final bucket ordering uses an unstable sort over a packed key
reproducing exactly what a stable sort would give --- the optimisation the
original paper specifies, made deterministic, which the reference's
\texttt{std::sort} does not guarantee.

Exactness is enforced, not asserted: output is identical across every thread
count (\shmDetChecks{} of \shmDetTotal{} checks) and against the reference, and
any drop in mapped or confidently-mapped reads blocks a merge.

\textbf{Memory, the larger result.} \shmRssRsMin--\shmRssRsMax~GB
single-threaded against \shmRssCpp~GB, a
\shmRssRatioMin--\shmRssRatioMax$\times$ reduction --- but what changes with the
ratio matters more. The reference sizes its accumulator against the genome, so
\shmRssCpp~GB is what it costs to map \emph{one} read and what it costs to map
millions: a property of the index, which a machine either has room for or
cannot run the tool at all. Sizing by the read's half-length makes it a
property of the query. Figure~\ref{fig:memorythreads} is why we call the
headline single-threaded: each worker carries its own accumulator, so peak RSS
bottoms at \shmRssRsFloor~GB at \shmRssRsFloorThreads{} threads --- under the
single-threaded figure, where bounded read-ahead dominates --- and reaches
\shmRssRsCap~GB at \shmCapThreads{} on \shmRssRsCapBench. Even that worst cell
keeps a \shmRssRatioCap$\times$ advantage, on cores the reference cannot use.

\textbf{Where the time goes.} Figure~\ref{fig:stages} gives every stage's share
of \texttt{query\_mapping} for all \shmNumCells{} cells. The costliest is
\texttt{\shmTopStage} at \shmTopStageShare\% of CPU on average: pointer-chasing
and latency-bound, which is why the profitable changes concerned the shape of
the data rather than the width of the arithmetic. The profile barely moves
between machines --- largest shift in any stage's share \shmShiftPP{}
percentage points, in \texttt{\shmShiftStage}, which is input reading.

\textbf{Thread scaling, and where it stops.} On \shmScaleXPeakBench{}
\texttt{\shmHostX} reaches \shmScaleXPeak$\times$ at \shmScaleXPeakThreads{}
threads then falls back; \texttt{\shmHostA} climbs monotonically to
\shmScaleAPeak$\times$ at \shmScaleAPeakThreads. Matrix medians
\shmScaleXKnee$\times$ against \shmScaleAKnee$\times$ at \shmKneeThreads{}
threads, \shmScaleXCap$\times$ against \shmScaleACap$\times$ at \shmCapThreads.
Not the instruction set: \texttt{\shmHostX} has \shmTopologyX{} against
\shmTopologyA. The ceiling is memory-bandwidth contention on the shared index,
appearing as soon as a run spans more than one socket; \texttt{numactl} to one
node recovers most of it.

\textbf{Accuracy is unchanged, and checked.} On the simulated benchmark, the
only input with ground truth, reads land within one read length of their true
position for \shmAccMin--\shmAccMax\% of reads by metric, and at most
\shmWrongQMax{} reads under any metric are placed wrongly while reported as
confident.

\textbf{Four things that did not pay}, recorded because a negative result
nobody writes down gets retried. The sketching loop is load-port bound at six
level-one loads per base, which sinks both SIMD (more lanes, same ports) and
two-bit packing (removes the wrong two loads). Prefetching the pruning lookups
is at best break-even. Per-node index replication --- five implementations, one
bypassing the allocator for correct placement --- was slower than doing nothing
wherever a run spanned more than one socket.

\section{Conclusion}

The headroom was not algorithmic: the change that mattered most was a data
structure sized by the query rather than by the reference. Every number, table
and figure here is regenerated from the committed result sets by scripts in the
repository, and CI fails if any drifts from what it reports.
