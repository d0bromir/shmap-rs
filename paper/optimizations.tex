\begin{abstract}
\noindent
\textbf{Summary:} shmap-rs is a Rust port of \emph{map-shmap}~\cite{shmap}
that is \shmSpeedupXMin--\shmSpeedupXMax$\times$ faster single-threaded and
uses \shmRssRatioMin--\shmRssRatioMax$\times$ less peak memory while producing
byte-identical output. This note accounts for where that came from.
\shmNumOptimizations{} deliberate changes are responsible, together with the
rewrite that carries them --- and the ablation below shows the rewrite is the
larger of the two. All \shmNumExactOptimizations{} preserve output exactly, and
each is compared against the upstream source it replaces at a pinned revision.
They are
presented in the order they had to be discovered: the cost structure the
algorithm implies, the data structure that structure argues for, the
algorithmic identities that let work be skipped, the parallel decomposition,
and only last the code. That order is the result rather than the presentation:
the largest wins are in the first two layers, and instruction-level work is
worth least here, and is where four further attempts measured
negative.\\[0.2em]
\textbf{Availability:} original \url{\shmUpstream}; this port
\url{https://github.com/d0bromir/shmap-rs}, \shmLicense, version~\shmVersion.
\end{abstract}

\section{The theoretical base}

\emph{map-shmap}~\cite{shmap} is Ivanov and Medvedev's, and nothing below
changes what it computes. It sketches read and reference by FracMinHash,
attributes each seed match to the overlapping fixed-width buckets whose window
contains it, prunes buckets with an admissible seed heuristic, and refines the
survivors with a sliding window. Its per-read cost has three factors --- reads,
matches examined, and a logarithmic term in reference size --- and the
important property for an implementer is which of them is paid in
\emph{arithmetic} and which in \emph{memory traffic}.

Almost all of it is memory traffic: seeds are looked up in an index far larger
than the last-level cache, the buckets they touch are scattered across an array
sized by the reference, and the refinement sweep walks a window last touched by
a different read. Profiling agrees: \texttt{\shmTopStage} is the costliest
stage at \shmTopStageShare\% of CPU on average, and pointer-chasing rather than
arithmetic. Two consequences order everything else. A change that reduces
\emph{how much memory is touched} outranks one that reduces instructions
issued, because the machine is waiting either way; and the sizes that matter
are those set by the \emph{reference}, since a whole-genome run cannot escape
them --- which points at the accumulator.

\section{The data structure}

The C++ allocates one dense bucket array per reference segment, sized so that
every window the algorithm could ever use has a slot (\texttt{buckets.h},
Table~\ref{tab:optimizations}). Its width is a compile-time minimum rather than
the width any particular read will use, so a human genome costs about fifteen
gigabytes before a single read is mapped, whether one read is mapped or
millions.

The observation that removes it is that \emph{a read can only touch buckets
within its own span}. The array does not have to be indexed by reference
bucket; it has to be indexed by the buckets this read can reach, which is set by
the read's own half-length. shmap-rs sizes it that way and keeps a sparse map as
the fallback, and the two paths are tested to agree exactly. The footprint stops
being a property of the genome and becomes a property of the query:
\shmRssRsMin--\shmRssRsMax~GB single-threaded against \shmRssCpp~GB, the lower
panel of Figure~\ref{fig:vscpp}.

\input{x86_64/fig_vs_cpp.tex}

One change, in one data structure, and it is most of the memory result. It also
removed a contention bottleneck that had made multithreading nearly useless: a
per-worker copy of a genome-sized array does not scale, and no thread tuning
would have rescued it. The data structure had to be right before the parallel
decomposition could be.
\section{The algorithmic identities}

Three changes skip work by proving it need not be done. None is an
approximation; each is an identity, and the byte-identical output is the check.

\textbf{The second-best search repeats the first.} Computing mapq needs the
second-best mapping, and the C++ searches for it with a second full pass over
the same surviving buckets (\texttt{shmap.h}, Table~\ref{tab:optimizations}). On
the two fixed-length metrics, scoring a bucket turns out to be a pure function
of its \emph{location}: it never reads the mutable state that pruning updates
between the passes, and it restores its own scratch exactly, so the second pass
can replay the first's scores. It is deliberately not applied to the two
bucket-based metrics, where the score is built out of exactly that mutable
state. Because the acceptance threshold ratchets upward during the first pass, a
bucket discarded late there can still clear the second pass's flatter cutoff ---
so the win is partial by construction, which is why it is roughly two calls in
five and not all of them.

\textbf{A repetitive seed does not need a hash map.} The C++ builds a fresh
scratch hash map per seed to accumulate its hits; the hits are already sorted,
so the map is redundant and the same buckets can be accumulated in place at
constant integer cost per hit.

\textbf{An unstable sort can reproduce a stable one.} Ordering the final buckets
by descending match count is the original paper's own
Algorithm~4 ``Optimization~2''. % lint-ok: the source paper's own numbering, a citation
Packing the tie-break into the sort key makes an unstable sort reproduce exactly
what a stable sort would give, over keys a quarter the size of the records. Here
the port is stronger than the source rather than merely faster: the C++'s
\texttt{std::sort} guarantees no particular order among equal keys, even between
its own runs, and this does.

\section{The parallel decomposition}

\shmNumParallelOptimizations{} of the \shmNumOptimizations{} exist only because
the C++ is single-threaded, so they replace nothing upstream: threaded read
mapping, hash-sharded index storage with chunked reference sketching, and a
two-pass count-then-fill FASTA reader. The constraint that shapes all three is
that output must not depend on thread count, which rules out any decomposition
whose result depends on completion order: a sketch window is a pure function of
the bases under it, a shard's contents are set by the hash rather than by which
worker filled it, and the FASTA reader's second pass writes what its first
counted. Determinism is checked rather than assumed, on every thread count
and benchmark (\shmDetChecks{} of \shmDetTotal{} checks).

\section{The code}

\input{figure_ablation.tex}

Only two of the \shmNumOptimizations{} are instruction-level, and they are last
because they are worth least. The sketching hot loop precomputes its rotation
tables, iterates without bounds checks, hashes once per lookup instead of twice,
and sizes its output buffer from the actual distribution. The allocation work
stores a single query position inline rather than in a one-element vector, has
matches borrow their seeds instead of copying them, indexes the difference
histogram densely, and discards the reference sequence after sketching, where
the C++ keeps a second full copy of the genome for the whole run.

Their effects are in Table~\ref{tab:optimizations}: real, but small beside the
first two layers. The stronger evidence for the ordering is negative ---
hand-written SIMD sketching, two-bit packing, software prefetching of the
pruning lookups, and per-node index replication implemented five ways, were each
built or probed at full scale and each measured a loss or a wash. The sketching
loop is load-port bound at six level-one loads per base, so more lanes add
pressure where there is none to spare, and packing removes the wrong two of
those loads. When a workload waits on memory, instruction-level effort is the
layer with least left in it.
\section{What each one is worth}

Table~\ref{tab:optimizations}'s effects were each measured against the build
that change landed on, months apart and on different inputs; they share no
baseline, machine or read set and do not sum, so the table cannot say how much
of the result is which change. Figure~\ref{fig:ablation} answers that, on the
whole genome on \shmAblHost{}, which has \shmAblCores{} cores and the memory
to hold the pre-optimization accumulator once per worker --- the reason the
figure could not be produced on a smaller machine. End to end the C++ is
\shmAblTotalX$\times$ the shipped mapper there and uses
\shmAblRssTotalX$\times$ the peak memory: Figure~\ref{fig:vscpp}'s headline,
reproduced inside the ladder's own protocol.

Every change is switchable at run time, in one instrumented build, back to the
code path it replaced --- one binary, one machine, one compiler, one input.
That is what makes a step
attributable, and attributable to that change \emph{given the ones to its
left}: what the parallel index is worth depends on whether each worker still
carries a genome-sized accumulator. Every bar's mapping is compared byte for
byte against the leftmost, a stricter test of the exactness claim than the
suite's. Those switches are not in the released mapper --- a branch that exists
only to be measured is paid for by everyone who runs the program --- so they
live on an
archived, never-merged branch, and the harness refuses a build that lacks them.
\shmAblNotRungs{} of the \shmNumOptimizations{} cannot be a rung and are
reported as absent rather than estimated: one is a capability rather than a
branch, the other type-level, as below.

\textbf{The step into the ladder is the largest, and it is not one of the
nine.} Getting from the C++ to \emph{pre-optimization} --- the port itself,
before any ablatable change is switched back on --- is \shmAblPortX$\times$,
against \shmAblLadderX$\times$ for the whole ladder that follows it; the two
compose by multiplication and return the \shmAblTotalX$\times$ measured
directly between the ends, which is what makes the decomposition checkable.
Two things sit in it: the allocation-and-layout row, which is type-level ---
matches borrow their seeds, the single-occurrence case is stored inline --- so
reversing it is a different program rather than a different branch, which is
why it cannot be a rung; and the rewrite itself, a different language,
allocator and standard library. This note does not separate them.

\textbf{Memory is where the layering is starkest.} The
\shmAblRssTotalX$\times$ splits \shmAblRssPortX$\times$ for the port against
\shmAblRssLadderX$\times$ for the ladder, and almost all of the second is one
bar: the accumulator the C++ sizes by the reference, a slot per
\shmMinHalflen{} bases of it. That is why the C++'s own footprint barely moves
between benchmarks --- \shmRssCppSpreadMB~MB across read sets differing by
more than an order of magnitude in size --- and why the ratio \emph{grows}
with worker count, from \shmAblRssRatioOne$\times$ to
\shmAblRssRatioMax$\times$ at \shmAblThreadsMax{}: the array is per worker, so
what was removed is multiplied by the thread count while what remains is not.

\section{What none of them changed}

All \shmNumExactOptimizations{} preserve output exactly, enforced rather than
claimed: the mapping is byte-identical across every thread count and against
the C++, ground-truth accuracy is unchanged at \shmAccMin--\shmAccMax\%, and any
drop in mapped or confident reads blocks a merge.
